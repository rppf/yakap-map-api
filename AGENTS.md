# AGENTS.md

Agent guidance for this repo. README.md is the user-facing doc (setup, endpoints, previews) — update it when behavior changes.

## Project shape

Read-only public API: Hono on Cloudflare Workers, Neon Postgres over the serverless HTTP driver (`kysely-neon` NeonDialect), ZenStack v3 ORM (Kysely-based — no Prisma runtime). Single package — `pnpm-workspace.yaml` only whitelists dependency build scripts; it is not a monorepo.

## Commands

- Core loop: `pnpm install` → `pnpm generate` → `pnpm dev`. `generate` must run before `typecheck`/`dev` — it produces the `zenstack/*.ts` modules (schema, model + input types) the code imports.
- `pnpm typecheck` (`tsc --noEmit`) is the only automated verification. There are no tests, no lint/format config, and no CI.
- `pnpm preview` / `pnpm preview:alias` upload a live preview without deploying. Caveats: previews hit the **production Neon DB**, are publicly reachable, and have no logs — debug locally with `pnpm dev`.

## Generated code — do not edit

- `zenstack/schema.zmodel` is the data-model source of truth. Edit only this file, then run `pnpm generate`.
- `zenstack/{schema,models,input}.ts` are regenerated by `pnpm generate` ("DO NOT MODIFY" headers) and are **committed** — v3 generates into the repo, not `node_modules`.
- `@zenstackhq/cli` (dev dep) provides the `zenstack`/`zen` bins and pulls in `prisma` + `@prisma/engines` transitively for its internals — keep both in the `pnpm-workspace.yaml` build allowlist or installs fail.

## Database

- The Neon `health_facilities` table is managed outside this repo — no migrations or seeding run here. Schema-change workflow: `pnpm exec zenstack db pull` (experimental — rewrites the zmodel in place; review the git diff and re-apply the `policy` plugin block + `@@allow` rule if dropped) → `pnpm generate`.
- PostGIS `coordinates` is `Unsupported("geography")` in the zmodel — geo filtering uses the plain `longitude`/`latitude` columns, never `coordinates`.
- `id` is BigInt in the DB; convert to `number` in responses (see `toDTO` in `facilities.service.ts`) — BigInt is not JSON-serializable.
- All DB access goes through `getDb()` (`src/lib/db.ts`): `ZenStackClient` + `NeonDialect` (Neon HTTP, no transactions) + `PolicyPlugin`. The zmodel policy `@@allow('read', true)` denies writes at the ORM level — keep the API read-only.

## Env / secrets

Two files, keep `DATABASE_URL` in sync between them:

- `.env` — used by `zen db pull` (datasource url)
- `.dev.vars` — used by `wrangler dev` (also `CORS_ORIGIN`; CORS falls back to `*` if unset)

Production secret: `wrangler secret put DATABASE_URL`. Never commit credentials.

## Conventions

- One directory per resource under `src/routes/` with a trio: `<name>.route.ts` (Hono + `zValidator`), `<name>.schema.ts` (zod), `<name>.service.ts` (DB access). Mount routes by chaining `.route()` in `src/app.ts` — the chained builder type is exported as `AppType` for `hono/client` RPC consumers (yakap-map-web); splitting into separate `app.route()` statements breaks the RPC type.
- `facilities.route.ts` uses `hono/cache` (Cloudflare Cache API, `cacheName: 'yakap-map-api'`) with `Cache-Control: public, max-age=3600` — all `/api/facilities` GET responses are cached at the edge for 1h. Facility data changes rarely (manual imports), so if you deploy new data expect up to 1h of stale responses.
- Worker env bindings are hand-typed in `src/env.ts` (`Bindings`) — update it when adding vars/secrets.

## Repository conventions

- End-to-end tests live under `armada/e2e/{feature}/`. Only qa writes there.
- Screenshots live under `armada/screenshots/{feature}/`.
- No emojis in code, comments, print statements or logging.
- Keep it simple: small modules, clear names, no defensive programming, no overengineering.
- Prefer popular, well-supported libraries over custom code.
- **Shipnames title format**: When invoking `task`, set `description` to the work-only title. Do not manually prefix `<Ship>` or `[role]`; the shipnames plugin auto-prefixes them.
- **Evidence-based receipts**: Subagent tasks require pasted evidence in the receipt `Evidence` block. No claim of done is accepted without evidence.


## Adaptive delivery

- Commodore infers risk; QA always active; evidence depth follows risk. Other roles stay standby.
- Ask user risk override only for ambiguity, high consequence, contract conflict, or downgrade.
- Dependency-ready phases and separate voyages run parallel; serialize shared writers. Group findings before fixes; only `BLOCKING` stops work. Use compact receipts.

## armada/ledgers/{feature}/DEFECTS.md — the defect ledger

All defects live in `armada/ledgers/{feature}/DEFECTS.md`, one entry per defect, newest
first. Writers: **qa** (create, close, reopen) and **orchestrator** (record developer
responses, reject). Nobody else edits it, ever.

Format, exactly:

    ## DEF-001: Short title

    - Status: OPEN
    - Severity: HIGH | MEDIUM | LOW
    - Found by: qa | adversary (ADV-003)
    - Phase: 3

    Steps to reproduce:
    1. Numbered, specific, starting from app launch.

    Expected: What should happen.
    Actual: What happens instead.
    Screenshot: armada/screenshots/{feature}/def-001.png (optional)

    History:
    - qa: opened

Statuses and who may set them:

| Status | Meaning | Set by |
|--------|---------|--------|
| OPEN | Filed, or reopened after a failed retest or a bounced dispute | qa |
| FIX-READY | A developer reports a fix is in | orchestrator, relaying the developer |
| DISPUTED | A developer reports CANNOT REPRODUCE or WORKING AS INTENDED | orchestrator, relaying verbatim |
| CLOSED | qa retested and confirmed the fix, or accepted the dispute | qa only |
| REJECTED | Will not fix, with a written reason | orchestrator only |

Every status change appends a History line. A defect is never done because a developer says
so — it is done when qa closes it.

## armada/ledgers/{feature}/ADVERSARIAL_REVIEW.md — the adversary's findings

All adversary findings live in `armada/ledgers/{feature}/ADVERSARIAL_REVIEW.md`. Writers: **adversary** (create
entries) and **orchestrator** (fill Disposition). Nobody else.

Format, exactly:

    ## ADV-001: Short title

    - Session: phase-3 gate | final
    - Suggested severity: HIGH | MEDIUM | LOW

    What I did: ...
    Expected: ...
    Actual: ...
    Screenshot: armada/screenshots/{feature}/adv-001.png (optional)

    Disposition: PENDING

The orchestrator replaces PENDING with either `ACCEPTED -> DEF-NNN` or `REJECTED - reason`.
Accepted findings are reproduced and filed in armada/ledgers/{feature}/DEFECTS.md by qa. No entry may remain PENDING
when the final phase completes.

## armada/ledgers/{feature}/SECURITY_FINDINGS.md — security findings

All security findings live in `armada/ledgers/{feature}/SECURITY_FINDINGS.md`. Writer: **security** (create findings).
Statuses: OPEN, ACCEPTED, REJECTED, MITIGATED. Orchestrator sets Disposition. Nobody else edits.

Format, exactly:

    ## SEC-###: Title

    - Status: OPEN
    - Severity: HIGH | MEDIUM | LOW
    - Found by: security
    - Phase: N

    What I found: ...
    Expected: ...
    Actual: ...
    Screenshot: armada/screenshots/{feature}/sec-###.png (optional)

    History:
    - security: opened

Statuses and who may set them:

| Status | Meaning | Set by |
|--------|---------|--------|
| OPEN | New finding, pending review | security |
| ACCEPTED | Finding confirmed, fix planned | orchestrator |
| REJECTED | Not a vulnerability / not in scope | orchestrator |
| MITIGATED | Fix applied and verified | orchestrator |

Every status change appends a History line. A finding is never done because security says
so — it is done when the orchestrator closes it.

## Phase gates

A phase in armada/REQUIREMENTS.md passes only when its
success criteria are demonstrated by evidence — a passing test run, a screenshot, or both. A
phase starts as soon as the phases it depends on have passed; independent phases run in
parallel as background subagents.
